Before starting: read `CLAUDE.md`, confirm every dependency is `done` in `tasks/STATUS.md`, run the account guard for any AWS write.

**Goal.** A Terraform-managed EKS service with a modern OIDC pipeline, running on a self-hosted runner.

**Build.** Terraform, state key `pagos/terraform.tfstate` in `condor-tfstate-<acct>`, applied as `condor-bootstrap`.
- **EKS cluster `condor-pagos`**
  - Version: the oldest version currently in standard support (PLANTED: AK-INF-03). Resolve it with `aws eks describe-cluster-versions` and record the version in the PR.
  - API endpoint: private only. Authentication mode: API.
  - One managed node group: `t3.medium`, desired 2, in the `app` subnets.
- **In-cluster setup**
  - AWS Load Balancer Controller via Helm, with IRSA or Pod Identity.
  - Namespace `pagos`.
- **Aurora MySQL** cluster `condor-pagos-db`, one `db.t4g.medium` instance, custom cluster parameter group `condor-pagos-params`.
- **Self-hosted GitHub Actions runner** EC2 `condor-gh-runner`. It lives in a **separate Terraform root `estate/iac/runner/`** with state key `runner/terraform.tfstate`, together with the IAM OIDC provider. It must never share a state file with Pagos: grouping treats everything in a runner's state file as platform tooling.
  - Amazon Linux 2023, `t3.small`, in the `app` subnets, with SSM Agent.
  - Registered to repo `condor-pagos` with label `condor-private`.
  - Instance role: SSM core only. It deploys by assuming the OIDC role below.
- **IAM OIDC provider** for `token.actions.githubusercontent.com`.
  - Role `condor-pagos-deploy`, trusting only `repo:<org>/condor-pagos:ref:refs/heads/main`.
  - Permissions: ECR push to `condor-pagos`, `eks:DescribeCluster`, and an EKS access entry scoped to namespace `pagos`.
- **ECR repository `condor-pagos`**: immutable tags, scan on push.
- **Private DNS**: NLB created by a Kubernetes Service, with record `pagos.condor.internal`.
- **CloudWatch alarm**: NLB unhealthy host count.
- **Workflows in `condor-pagos/.github/workflows/`**, both `runs-on: [self-hosted, condor-private]`:
  - `deploy.yml`: on push to `main`, test, build, push the image tagged with the commit SHA, then `helm upgrade --install pagos chart/ -n pagos` with that image digest.
  - `infra.yml`: `workflow_dispatch` only. Placeholder for Terraform changes through CI, with a separate OIDC role `condor-pagos-tf-ci`. This is the legitimate path that P1-13's laptop apply contrasts with.
- **Tags**: none, with two exceptions. Kubernetes resources carry the label `app.kubernetes.io/name=pagos`. Tags that EKS and the AWS Load Balancer Controller add automatically, such as `elbv2.k8s.aws/cluster` and `service.k8s.aws/stack`, are expected and must not be removed.

**Acceptance**
- [ ] `terraform apply` succeeds, and the state object exists in the estate state bucket.
- [ ] A push to `condor-pagos` main runs `deploy.yml` on the self-hosted runner and the pod becomes Ready.
- [ ] From a Tienda instance: `curl pagos.condor.internal/health` returns 200.

**Cost limit.** USD 0.60/hour.

**Stop and ask if** the private endpoint cannot be reached from the runner, or the chosen EKS version cannot be created.
