# P4-06 · Pipeline linking, manual deploys and DORA

Before starting: read `CLAUDE.md`, confirm every dependency is `done` in `tasks/STATUS.md`, run the account guard for any AWS write.

**Goal.** Know which pipeline really deploys which app, which deploys bypassed pipelines, and how well each app ships.

**Build**
- **Spec `docs/specs/pipelines.md`, then implementation in Lambda `dp-pipeline-link`**:
  1. **Intent**: run the `dp_parsers` on the latest collected definitions (CodePipeline, buildspec, appspec, workflow YAML, Jenkinsfile, config.xml) to produce `DeployIntent` rows.
  2. **Confirmation**: an intent is confirmed for app X when both hold:
     - At least one CloudTrail event matching its mechanism (`CreateDeployment` → CodeDeploy app/group; `UpdateService` → cluster/service; `SendCommand` → targets) resolves to X.
     - The event occurred within a run of that pipeline's time window (from run start to run end + 10 minutes), with a principal matching the intent's `credential_mode`:
       - CodePipeline or CodeBuild service role
       - OIDC role session for GitHub
       - the Jenkins instance profile session
     - Helm deploys have no CloudTrail event. Confirm them instead through the image trace: the digest pushed in the run is running in namespace X after the run.
  3. **Link**: `relation(deploys_to)` from pipeline to app, confidence 0.85 (ladder), source `pipeline_deploy_target`. Evidence links to the definition record and the confirming event (AK-PIP-01).
  4. **Manual deploy detection**, after `history_start`, for deploy-class events: `PutImage`, `UpdateService`, `RegisterTaskDefinition`, `CreateDeployment`, `ExecuteChangeSet`, `UpdateStack`, tfstate `PutObject`.
     - Parameter group modifications are **not** deploy-class. They are drift, handled by `R-INF-DRIFT`.
     - Ignore events where `userIdentity.invokedBy` is an AWS service, such as CodeDeploy deployments started by Auto Scaling.
     - If the principal is an IAM user, or an assumed role not used by any pipeline, and no pipeline run overlaps the event's window for that target, it is a manual deploy (AK-PIP-02, AK-PIP-03).
     - `condor-bootstrap` and `dp-deployer` events are excluded.
  5. **Image trace**: using `image_trace` relations, flag running images whose digest has no pipeline run that pushed it (AK-PIP-02).
  6. **DORA per app**, window from `history_start` to now:
     - `deploy_frequency`: successful production deploys per day, where a production deploy is a confirmed deploy event or a successful Helm image-trace deploy.
     - `change_failure_rate`: failed deploys divided by all deploys. A deploy fails if the pipeline run failed at or after its deploy stage, or if a failure is followed by a fix commit within 24 hours.
     - `lead_time`: median time from commit author date to successful deploy, for commits included in that deploy.
     - `time_to_restore`: median time from a failed deploy to the next successful deploy.
     - Writes `assertion` rows per app.
- **dbt mart `mart_delivery`**: per app, the pipeline links, CI system, credential mode, approval flag, test-stage flag, DORA metrics, and manual deploy counts.
