**Goal.** Repeatable, logged activity so DORA metrics, flow-log dependencies and utilisation have real data. Expected metrics come from the ledger, never from hard-coded numbers.

**Build**
- **Ledger `estate/harness/ledger.jsonl`**. One line per generated action:
  - Fields: `ts`, `app`, `kind` (`commit`, `expected_build_fail`, `expected_deploy_fail`, `fix`, `manual_push`, `planted_change`), `repo`, `sha`, `note`.
  - A small uploader copies it to `s3://condor-harness-ledger-<acct>/` after each run. That bucket has no tags. It is estate data, but the platform must never read it: only the evaluation harness does.
- **Workflows in `condor-harness`**. Scheduled with GitHub Actions `schedule`, using a fine-grained PAT stored as a repo secret. The GitHub App built in P2-04 is **not** installed on this repo.
  - `commits.yml`, every 3 hours: commits a trivial change to one of `condor-tienda`, `condor-pagos` or `condor-reportes`, round-robin.
    - Every 5th commit per app adds `FAIL_BUILD`; the next commit removes it (`expected_build_fail`, then `fix`).
    - Once per app per week, commit a runtime-breaking config so deploy fails, then the fix (`expected_deploy_fail`, then `fix`).
  - `inventario-push.yml`, twice a week: using `dev.juan`'s keys, build and push `condor-inventario:latest`, then `aws ecs update-service --force-new-deployment` (`manual_push`, PLANTED: AK-PIP-02).
  - `tienda-approve.yml`: approves pending Tienda manual approvals after 10 minutes, through a scoped IAM role assumed with OIDC from `condor-harness`. Record it in the ledger.
- **In-VPC traffic**, needing no harness infrastructure:
  - Tienda instances: systemd timer calling `/checkout` every minute. It produces Tienda → Pagos traffic.
  - Inventario: its own 5-minute DB read, already built.
  - Reportes worker: its own cron, already built.
  - Jenkins: nightly export by cron. The harness also triggers it through the API three times in week one.
- **`estate/harness/expected_metrics.py`**: computes per-app deploy frequency, change failure rate and lead time from the ledger joined with pipeline run results. It uses only entries with `ts` at or after `history_start` from `estate/verify/history-start.json`, and exits with an error if that file is absent. Output goes to `answer-key/expected/dora.json`.

**Acceptance**
- [ ] After 24 hours, the ledger has at least 8 commits across three apps, and each pipeline has at least 2 runs.
- [ ] `uv run estate/harness/expected_metrics.py` produces `dora.json` for all three apps.
