# P4-04 · Grouping engine

| Field | Value |
|---|---|
| Phase | Phase 4 · Process for dashboards |
| Stream | I |
| Depends | P4-02, P4-03 |
| Gate | `none` |
| Paths | platform/processing/grouping/ |

Before starting: read `CLAUDE.md`, confirm every dependency is `done` in `tasks/STATUS.md`, run the account guard for any AWS write.

**Goal.** Every in-scope resource assigned to an application, platform tooling, governance, shared infrastructure or ungrouped, exactly as the grouping spec says.

**Build.** Lambda `dp-grouping`, implementing `docs/specs/grouping.md` exactly.
- **Inputs**: `entity`, `identity_link`, and dbt staging models for CloudFormation, tfstate, ECS, EKS (Kubernetes namespaces), ELB, ASG, tags and SSM Inventory, plus flow aggregates. Pipeline deploy-target signals are read if P4-06 has run; the engine re-runs after P4-06 in the state machine.
- **Outputs**
  - `entity` rows of type `application`, `platform_tooling` and `governance`.
  - `relation(member_of)` rows with confidence and source.
  - `assertion` rows recording which signal decided.
  - `adjudication` rows for conflicts.
  - `evidence` rows.
- **Validation override**: if `validation_state.status` is `reassigned`, `confirmed` or `corrected` for a resource, that decision overrides the computed membership with confidence 1.0, and source `owner_validation`.
- **dbt mart `mart_grouping_coverage`** (AK-GRP-11).

**Acceptance**
- [ ] Unit tests reproduce every worked example in the spec, from fixtures.
- [ ] `answer-key/trace/processed_checks.yaml` gains queries for AK-GRP-01 to AK-GRP-11, and they pass against the integration run.
